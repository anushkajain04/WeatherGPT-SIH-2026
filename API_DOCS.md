# WeatherGPT RAG Pipeline - API Documentation

This document describes the REST API exposed by the `rag_pipeline` microservice. The MERN backend should use these endpoints to generate weather forecasts and answer user queries.

## 🌐 Base URL
**Production:** `https://weathergpt-sih-2026-stjn.onrender.com`
**Local Development:** `http://localhost:8000`

## 🔐 Authentication
The `/chat` endpoint is protected by a shared-secret API key. 
All requests to protected endpoints MUST include the following header:
- `X-Internal-API-Key`: *(Get this value from your `.env` file or Render dashboard. The default for local testing is `-zx*f]g}VrTM^67~o[`)*

---

## 📡 Endpoints

### 1. `GET /health`
Used to check if the server is awake and healthy. This does **not** require authentication.

**Request:**
```http
GET /health
```

**Response (200 OK):**
```json
{
  "status": "ok"
}
```

---

### 2. `POST /chat`
The core endpoint for the Generative AI pipeline. It automatically routes the query, fetches live weather data or vector database context, and returns a natural language response.

**Request:**
```http
POST /chat
Content-Type: application/json
X-Internal-API-Key: <YOUR_INTERNAL_API_KEY>
```

**Request Body (JSON):**
| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `query` | string | **Yes** | - | The user's question (e.g. "What is the temperature today?") |
| `role` | string | No | `"normal_user"` | The persona for the LLM (e.g. `"farmer"`, `"normal_user"`) |
| `location` | string | No* | `null` | The city/location. **(*Required only if the query asks about a specific forecast like temperature or rain)** |

**Example Request Body:**
```json
{
  "query": "Will it rain in Ludhiana tomorrow?",
  "role": "farmer",
  "location": "Ludhiana"
}
```

**Response Body (200 OK):**
| Field | Type | Description |
|---|---|---|
| `answer` | string | The final natural language response generated by the LLM. |
| `route` | string | Either `"structured"` (live weather data) or `"semantic"` (knowledge base query). |
| `model_used` | string | `"primary"` (Groq) or `"fallback"` (Gemini). |
| `latency_seconds` | float | Time taken to generate the answer. |
| `location_resolved` | string \| null | The formally recognized name of the location used for weather fetching (if applicable). |

**Example Success Response:**
```json
{
  "answer": "Yes, light rain is expected in Ludhiana tomorrow. Please ensure your crops are protected.",
  "route": "structured",
  "model_used": "primary",
  "latency_seconds": 1.25,
  "location_resolved": "Ludhiana"
}
```

### ⚠️ Error Codes (HTTP Status)
The MERN backend should be prepared to handle these status codes:

- **`400 Bad Request`**:
  - *Cause:* The query was routed to the structured weather lane, but the `location` field was missing in the request body.
  - *Cause:* The provided `location` could not be resolved by the geocoder (e.g., "AsdfQwerZxcv").
- **`401 Unauthorized`**:
  - *Cause:* The `X-Internal-API-Key` header was missing or incorrect.
- **`503 Service Unavailable`**:
  - *Cause:* Both the primary (Groq) and fallback (Gemini) LLMs failed to respond (e.g. API limits exceeded or network outage). 
  - *Action:* The MERN backend should show a polite error to the user like "Our AI systems are currently busy, please try again later."
- **`500 Internal Server Error`**:
  - *Cause:* An unexpected crash occurred in the pipeline.

## ⚡ Important Notes for Backend Developers
1. **Cold Starts:** Since this is hosted on Render's free tier, the server falls asleep after 15 minutes of inactivity. **The very first request after a sleep period will take 30-60 seconds.** Subsequent requests will be fast (under 2 seconds).
2. **Location Handling:** Do not ask the user to type their location manually. The MERN frontend should automatically detect the user's location via GPS/IP, and the MERN backend should inject that into the `location` field of this API request silently!
